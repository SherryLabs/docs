The Actions API exposes the same primitives the [Widget Kit](/widget/overview) uses internally: transaction builders, swap routing, and protocol/token metadata. If the prebuilt widget covers your use case, **start there** — it handles UI, passkey UX, and chain switching for you. The endpoints below are documented so you can build your own UI on top of the same primitives.

## What's in this group

<CardGroup cols={2}>
  <Card title="Builders" icon="hammer">
    Serialize an on-chain transaction (swap, transfer, cross-chain). No signing, no broadcast — just the encoded calldata + chain hints. You sign and broadcast yourself (or hand off to the Signing flow).
  </Card>
  <Card title="Execute (Swap)" icon="arrows-rotate">
    Quote + prepare/confirm pair for direct DEX swaps. The `confirm` step requires a passkey-stamped activity (same pattern as `transactions/confirm`) — backend alone cannot complete it.
  </Card>
  <Card title="Directory" icon="book">
    Catalog of supported protocols per chain. Used to discover what's wired in before calling a builder.
  </Card>
  <Card title="Tokens" icon="coins">
    Token list for a given `(chain, protocol)`. Used to populate UI dropdowns and validate destination tokens.
  </Card>
</CardGroup>

## Why these aren't backend-only

The Widget Kit is the recommended integration path — it ships the swap, transfer, and bridge UX for you. These endpoints exist for two cases:

1. **Self-built UX** — you want full control over the swap UI and don't want to embed the Sherry widget. Use Builders to construct the tx, then drive your own signing flow.
2. **Backend orchestration** — you need to quote, validate, or pre-build a transaction server-side before handing it to the user's device.

For the swap `prepare → confirm` flow specifically, the confirm step **requires a passkey-stamped activity** in the request body. Your backend can prepare; the user's device (with the registered passkey) must sign. This mirrors the [transaction signing flow](/api-reference/flows/transaction-signing).

## What's not here

- **Lending / yield / earn** — not currently exposed via API.
- **Cross-chain bridge UX** — `POST /action/builders/crosschain-bridge` returns the serialized tx, but the destination-chain settlement is async (no `prepare/confirm` pair). Track via your own indexer or the Widget Kit's lifecycle events.
- **Approval flows** — ERC-20 approvals are handled by the Widget Kit. If you build your own UX, you handle approvals yourself before calling the builder.
